# ローカルMarkdownチケット管理ツール 仕様書

## 1. 目的

ローカル環境で、Markdownファイルを用いてタスク・不具合・調査事項などのチケットを管理する。

本ツールは人間による直接編集だけでなく、GitHub Copilot CLI、Codex、Claude CodeなどのAIエージェントからチケットを作成・更新・完了させることを主目的とする。

専用DBや外部サービスには依存せず、すべての情報をGit管理可能なテキストファイルとして保持する。

---

## 2. 基本方針

- データ形式はMarkdownとする
- 1チケット = 1ファイルとする
- Gitで履歴管理できること
- AIが構造を理解しやすい形式とする
- AIが既存チケットを安全に更新できること
- 専用アプリがなくても閲覧・編集可能であること
- ローカル環境のみで完結できること
- Markdown本文には自由記述を許可する
- チケットの主要属性はFront Matterで管理する

---

## 3. ディレクトリ構成

```text
tickets/
├── README.md
├── backlog/
├── doing/
├── blocked/
└── done/
```

チケットの状態に応じてファイルを各ディレクトリへ配置する。

例:

```text
tickets/
├── backlog/
│   ├── TICKET-001-login-error.md
│   └── TICKET-002-add-search.md
├── doing/
│   └── TICKET-003-refactor-api.md
├── blocked/
└── done/
    └── TICKET-004-fix-cookie.md
```

---

## 4. チケットID

チケットIDは以下の形式とする。

```text
TICKET-001
TICKET-002
TICKET-003
```

IDは一度発行したら変更しない。

削除済み・完了済みのIDも再利用しない。

---

## 5. ファイル名

以下の形式とする。

```text
<ID>-<slug>.md
```

例:

```text
TICKET-001-login-error.md
TICKET-002-session-storage.md
```

slugは英数字とハイフンを使用する。

チケットタイトルを変更しても、原則としてファイル名は変更しなくてよい。

---

## 6. チケットフォーマット

各チケットはYAML Front MatterとMarkdown本文で構成する。

```md
---
id: TICKET-001
title: ログインエラーを修正する
status: backlog
priority: high
created_at: 2026-09-10
updated_at: 2026-09-10
tags:
  - bug
  - auth
---

# ログインエラーを修正する

## 概要

特定条件でログイン処理が失敗する。

## 背景

Cookieの状態によって認証処理が正常に動作しない可能性がある。

## 対応内容

- [ ] 再現条件を確認する
- [ ] 原因を特定する
- [ ] 修正する
- [ ] テストを追加する

## 調査メモ

未調査。

## 対応結果

未対応。
```

---

## 7. 必須属性

Front Matterには以下を必須とする。

| 項目説明 | |
| --- | --- |
| id | チケットID |
| title | チケットタイトル |
| status | 現在の状態 |
| priority | 優先度 |
| created_at | 作成日 |
| updated_at | 最終更新日 |
| tags | 分類タグ |

---

## 8. status

statusは以下のみ使用可能とする。

```text
backlog
doing
blocked
done
```

意味は以下。

### backlog

未着手。

### doing

対応中。

### blocked

外部要因などにより対応を進められない状態。

### done

対応完了。

---

## 9. priority

priorityは以下の4種類とする。

```text
low
medium
high
critical
```

---

## 10. Markdown本文

本文には以下のセクションを基本構成として使用する。

```text
概要
背景
対応内容
調査メモ
対応結果
```

不要なセクションは省略可能。

ただしAIによる更新を容易にするため、既存セクション名は可能な限り変更しない。

---

## 11. チェックリスト

作業項目はMarkdownのチェックリストで管理する。

```md
## 対応内容

- [x] 再現確認
- [x] 原因調査
- [ ] 修正
- [ ] テスト追加
```

AIは作業完了時に対象項目を `[x]` に更新する。

---

## 12. AIによるチケット作成

AIに新規チケット作成を依頼した場合、以下を行う。

1. 既存チケットを確認する
2. 重複するチケットが存在しないか確認する
3. 最大のチケットIDを確認する
4. 次のIDを採番する
5. `tickets/backlog/` にMarkdownを作成する
6. `created_at` と `updated_at` に現在日を設定する

例:

```text
「Cookieのpath競合について調査するチケットを作成して」
```

生成結果:

```text
tickets/backlog/TICKET-021-cookie-path-conflict.md
```

---

## 13. AIによるチケット開始

AIが作業を開始した場合、

```yaml
status: backlog
```

を

```yaml
status: doing
```

へ変更する。

同時にファイルを

```text
tickets/backlog/
```

から

```text
tickets/doing/
```

へ移動する。

`updated_at` も更新する。

---

## 14. AIによるチケット更新

AIが調査・実装を行った場合、チケットへ作業内容を追記する。

例:

```md
## 調査メモ

2026-09-10

原因を確認。

Cookieのpathが `/` と `/app` の2種類存在しており、
同名Cookieがブラウザから送信されていた。
```

重要な判断・原因・対応方針は可能な限りチケットへ残す。

単なる作業ログを大量に記録する必要はない。

---

## 15. AIによるチケット完了

すべての対応が完了した場合、

```yaml
status: done
```

へ変更する。

ファイルを

```text
tickets/done/
```

へ移動する。

また、`対応結果` を更新する。

例:

```md
## 対応結果

Cookie名を変更し、同名Cookieが複数送信されないよう修正した。

回帰テストを追加し、問題が解消されたことを確認した。
```

---

## 16. blocked

作業が進められない場合、

```yaml
status: blocked
```

へ変更し、

```text
tickets/blocked/
```

へ移動する。

本文へ理由を記載する。

```md
## Blocked理由

API仕様の確定待ち。

関連仕様が確定後に作業を再開する。
```

---

## 17. AI更新ルール

AIがチケットを更新するときは以下を遵守する。

- IDを変更しない
- `created_at` を変更しない
- 更新時は `updated_at` を変更する
- 未確認事項を事実として記載しない
- 推測と確認済み情報を区別する
- 既存の記録を理由なく削除しない
- statusとディレクトリを一致させる
- 完了していない項目を `[x]` にしない
- 意思決定や重要な調査結果を記録する
- 不要な文章を大量に追記しない

---

## 18. AIへの共通指示

リポジトリルートに以下のようなAI向けルールを配置する。

例:

```text
AGENTS.md
```

内容:

```md
# Ticket Management Rules

このリポジトリでは `tickets/` 以下のMarkdownでチケットを管理する。

作業開始前に関連するチケットを検索すること。

関連チケットが存在する場合、そのチケットを更新する。

存在しない場合、必要に応じて新規チケットを作成する。

作業開始時:

- statusをdoingに変更
- tickets/doingへ移動

作業中:

- 重要な調査結果
- 原因
- 判断理由
- 実装方針

をチケットに記録する。

作業完了時:

- checklistを更新
- 対応結果を記載
- statusをdoneに変更
- tickets/doneへ移動

チケット管理のためだけに不要な情報を生成しない。
```

---

## 21. MVP

初期バージョンでは以下のみ実現する。

```text
Markdown
+
Git
+
AGENTS.md
```

専用CLIやDBは作成しない。

AIがファイル操作・検索・更新を直接行うことでチケット管理を成立させる。

ツールそのものを複雑にせず、

「AIが読み書きしやすいチケットフォーマット」

を提供することを本ツールの中心的な価値とする。
